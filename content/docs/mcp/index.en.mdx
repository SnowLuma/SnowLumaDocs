`@snowluma/mcp` exposes SnowLuma's OneBot action catalog and optional execution through stdio. Existing tool names, parameters, text results, and read/write gates remain compatible. Capable clients can also use input completion, background tasks, event subscriptions, and a message preview panel.

This section follows the [current development branch](https://github.com/SnowLuma/SnowLuma/tree/dev/packages/mcp). New capabilities require a package containing those changes; a source update does not establish npm availability. Check your installed release. The bundled catalog is a snapshot, not proof that a connected server supports every action.

## Modes

| Mode | Activation | Capabilities |
| --- | --- | --- |
| `docs` | No endpoint, or explicitly selected | Catalog, local runtime overview, and message drafts; no contact with a running SnowLuma instance. |
| `read` | Default with an endpoint | Adds actions explicitly marked read-only and optional event subscriptions. |
| `write` | Explicit `SNOWLUMA_MCP_MODE=write` | Adds writes and streaming; configured tasks also require a capable client. |

Classification comes from action definitions, not name prefixes such as `get_`. Every execution checks the mode even when a client calls an unlisted tool directly. All current stream actions, including downloads, require write mode.

## Requirements

- A client supporting stdio MCP servers.
- Node.js `^24.22.1 || >=26.12.1`, with `node` or `npx` available to that client.
- Execution requires the configured **OneBot HTTP endpoint**, such as `http://127.0.0.1:3000/`, not the WebUI management port.
- Events require a separately configured OneBot WebSocket event endpoint; its address is not inferred from HTTP.

The same command supports MCP `2026-07-28` discovery and legacy initialization. Existing clients keep their launch configuration. Advanced features also depend on declared client capabilities. This command does not expose a listening MCP HTTP server.

## Docs-only mode

For clients using the `mcpServers` configuration format:

```json
{
  "mcpServers": {
    "snowluma": {
      "command": "npx",
      "args": ["-y", "@snowluma/mcp"]
    }
  }
}
```

| Tool | Purpose |
| --- | --- |
| `list_actions` | Filter by category, read-only status, or streaming; optionally paginate. |
| `search_actions` | Substring search by default; optional keywords and common Chinese/English synonyms. |
| `get_action` | Parameters, constraints, result schemas, and examples; aliases accepted. |
| `list_categories` | Categories and action counts. |
| `get_runtime_info` | Local overview by default; explicit connection checks require execution mode. |
| `preview_message` | Plain-text and quoted-reply drafts; calling the tool sends nothing. |

The `snowluma://onebot/actions` resource contains the complete catalog. See [Action discovery and results](/en/docs/mcp/actions).

## Connect to SnowLuma

Check the OneBot HTTP address and access token in the WebUI network adapter settings. This enables read-only execution:

```json
{
  "mcpServers": {
    "snowluma": {
      "command": "npx",
      "args": ["-y", "@snowluma/mcp"],
      "env": {
        "SNOWLUMA_MCP_ENDPOINT": "http://127.0.0.1:3000/",
        "SNOWLUMA_MCP_TOKEN": "your-access-token"
      }
    }
  }
}
```

`127.0.0.1` refers to the machine running MCP. Use the actual server address for remote connections. Inject credentials through client configuration rather than prompts.

Execution mode provides `query_action({ action, params? })` and `query_action_with_input`, which can ask the user for missing required parameters. Complete arguments still work with the original tool.

## Enable write mode

Add `"SNOWLUMA_MCP_MODE": "write"` to `env` to expose `invoke_action({ action, params?, execution? })` and `invoke_action_with_input`. Writes can send messages or change group settings; control their use through your client's authorization policy.

The following `env` also enables optional services. Keep only the services you need. Directories are on the **MCP host**:

```json
{
  "SNOWLUMA_MCP_MODE": "write",
  "SNOWLUMA_MCP_ENDPOINT": "http://127.0.0.1:3000/",
  "SNOWLUMA_MCP_TOKEN": "your-access-token",
  "SNOWLUMA_MCP_UPLOAD_ROOT": "/home/me/mcp-share",
  "SNOWLUMA_MCP_STREAM_DIR": "/home/me/mcp-downloads",
  "SNOWLUMA_MCP_TASK_DIR": "/home/me/private-mcp-tasks",
  "SNOWLUMA_MCP_EVENTS_URL": "ws://127.0.0.1:3001/event"
}
```

## Environment variables

| Variable | Meaning |
| --- | --- |
| `SNOWLUMA_MCP_ENDPOINT` | OneBot HTTP endpoint; absent means docs-only mode. |
| `SNOWLUMA_MCP_TOKEN` | Token shared by HTTP and event connections, sent in authorization headers. |
| `SNOWLUMA_MCP_MODE` | `docs`, `read`, or `write`. |
| `SNOWLUMA_MCP_TIMEOUT_MS` | Default `30000` ms. Ordinary request timeout; separate connection and per-read idle deadlines for streams. |
| `SNOWLUMA_MCP_STREAM_DIR` | Download output directory; defaults to `onebot-mcp-downloads` inside the system temporary directory. |
| `SNOWLUMA_MCP_UPLOAD_ROOT` | Existing directory allowed for automatic uploads; omitted means automatic local-file upload is disabled. |
| `SNOWLUMA_MCP_MAX_STREAM_BYTES` | Positive per-file byte limit, at most and defaulting to `4294967296`. |
| `SNOWLUMA_MCP_TASK_DIR` | Absolute private directory for task records; requires write mode and an endpoint. |
| `SNOWLUMA_MCP_EVENTS_URL` | Explicit `ws:` / `wss:` event address, without credentials, query parameters, or fragments. |

## Suggested workflow

1. Find actions with `search_actions`; inspect parameters, result schemas, and identifier sources with `get_action`.
2. Inspect configuration with `get_runtime_info`; set `check_connection: true` only when a live check is intended.
3. Use `query_action` for reads and `invoke_action` for writes. Their `_with_input` variants can collect missing required parameters.
4. Use background tasks for long transfers and event subscriptions for later messages.
5. Inspect business responses and diagnostics; a completed call is not proof of message delivery.

## Safety boundaries

Actions must exist in the bundled catalog and pass the mode gate. Catalog queries and the default overview stay offline; event sockets open only when the subscription tool is called. Cancellation or timeout does not undo remote effects and does not cause an automatic retry. Ordinary business failures retain the OneBot envelope: inspect `status`, `retcode`, and structured diagnostics. Parameter, transport, and stream protocol errors remain explicit failures.
